# 0001 — 서버 측 API 계층의 구현체

- 상태: **확정**
- 결정일: 2026-09-02
- 관련 문서: `docs/ARCHITECTURE.md`, `CLAUDE.md`

---

## 배경

Samantha는 AI 모델을 호출한다. AI API Key는 절대 모바일 앱에 둘 수 없다.
앱은 사용자 기기에 설치되므로, 앱에 포함된 값은 어떤 방식으로 숨기더라도 추출될 수 있다.

따라서 `모바일 앱 → 서버 측 API 계층 → AI 모델` 경로가 강제된다.
이 서버 측 API 계층을 무엇으로 구현할 것인가를 결정한다.

또한 이 계층은 단순 프록시가 아니다. 향후 다음을 담당한다.

- AI 대화 처리
- 장기 기억 처리
- 관계 엔진
- 결제 영수증 검증
- 푸시 알림 발송
- 사용량 제한
- 안전 정책 적용
- 로깅

---

## 고려한 선택지

### A. Supabase Edge Functions

Supabase가 제공하는 서버리스 함수(Deno 런타임)에 API 계층을 얹는다.

### B. 독립 백엔드 애플리케이션

Supabase와 분리된 별도의 서버 애플리케이션을 운영한다.

### 비교

| 항목 | A. Edge Functions | B. 독립 백엔드 |
|---|---|---|
| 관리 대상 인프라 | Supabase 하나 | Supabase + 백엔드 호스팅 |
| 초기 비용 | 무료 | 월 $5~10 수준 |
| 학습 부담 | 낮음 | 중간 (배포, 환경변수, 운영) |
| 실행 환경 | Deno | Node 계열 (앱과 언어 일관성) |
| AI 응답 스트리밍 | 가능하나 실행 시간 제약 | 제약 적음 |
| **백그라운드 작업** | **어려움** | 용이 |
| **정기 실행 작업** | **제한적** | 용이 |
| 로깅 / 모니터링 도구 선택 | 제한적 | 자유 |
| 벤더 종속 | 높음 | 낮음 |
| 참고 자료의 양 | 적음 | 많음 |

---

## 결정

**B. 독립 백엔드 애플리케이션을 사용한다.**

---

## 이유

1. **Samantha의 핵심 기능이 백그라운드 작업을 요구한다.**
   - 장기 기억: 대화 종료 후 기억 추출·정리·저장을 사용자 응답과 분리해 수행해야 한다.
   - 먼저 연락(알림): 사용자 상태를 주기적으로 확인하고 발송 시점을 판단해야 한다.

   이 두 기능은 부가 기능이 아니라 제품의 정체성이다. (`docs/PRODUCT.md` 2장)
   그리고 A에서 가장 다루기 어려운 영역이다.

2. **이 계층은 프록시가 아니라 비즈니스 로직의 중심이 된다.**
   결제 검증, 사용량 제한, 안전 정책, 관계 엔진이 모두 여기에 위치한다.
   함수 단위 실행 모델보다 하나의 애플리케이션으로 관리하는 편이 유지보수에 유리하다.

3. **상용 서비스 운영을 전제로 한다.**
   장애 대응, 로깅, 모니터링 도구 선택의 자유가 필요하다.

4. **전환 비용의 비대칭.**
   A로 시작해 Phase 5에서 B로 옮기는 비용이, 지금 B를 시작하는 비용보다 크다.

---

## 결과로 따라오는 것

- 백엔드 호스팅 대상을 하나 더 관리해야 한다.
- 배포 파이프라인이 앱과 백엔드 두 갈래가 된다.
- Supabase JWT 검증을 백엔드에서 직접 수행해야 한다.
- 개발 / Staging / Production 각 환경마다 백엔드 인스턴스가 필요하다.
- 월 고정 비용이 발생한다.

---

## 되돌릴 때의 비용

B → A 전환은 다음을 필요로 한다.

- 백엔드 코드를 Deno 런타임에 맞게 재작성
- 백그라운드 작업과 정기 실행 작업을 다른 방식으로 재설계 (가장 큰 비용)
- 배포 파이프라인 재구성

**전환 비용은 중간 수준이며, 시간이 지날수록 커진다.**
따라서 백엔드는 특정 호스팅에 종속되지 않는 형태로 작성한다.
(호스팅별 고유 기능에 의존하지 않는다)

- 백엔드 호스팅 서비스
- 배포 방식 및 CI/CD 서비스
