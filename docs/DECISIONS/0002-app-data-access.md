# 0002 — 모바일 앱의 데이터 접근 경로

- 상태: **확정**
- 결정일: 2026-09-02
- 관련 문서: `docs/ARCHITECTURE.md`, `docs/DATABASE.md`, `docs/DECISIONS/0001`

---

## 배경

Supabase 는 클라이언트가 데이터베이스에 직접 접근하는 것을 전제로 만들어진 서비스다.
앱에 `anon key` 를 넣고 RLS(Row Level Security)로 행 단위 접근을 통제하는 방식이 표준 사용법이다.

한편 `DECISIONS/0001` 에서 독립 백엔드를 두기로 했다.
따라서 앱이 데이터를 읽고 쓰는 경로가 두 가지로 갈릴 수 있다.

이 문서는 **앱이 Supabase 에 직접 접근할 것인가**를 결정한다.

---

## 고려한 선택지

### 가. 직접 접근 허용 (하이브리드)

앱이 Supabase 에 직접 접근해 데이터를 조회한다. RLS 로 보호한다.
쓰기와 AI 호출, 관계 갱신 등은 백엔드를 경유한다.

### 나. 백엔드 단일 창구

앱은 데이터베이스에 직접 접근하지 않는다.
모든 데이터 조회와 변경은 백엔드 API 를 통해서만 이루어진다.

### 비교

| 항목 | 가. 직접 접근 | 나. 백엔드 단일 창구 |
|---|---|---|
| 응답 속도 | 약간 빠름 | 한 단계 경유 |
| 백엔드 개발량 | 적음 | **많음** (조회 API 를 모두 구현) |
| 보안 통제 지점 | RLS + 백엔드 (두 곳) | 백엔드 (한 곳) |
| RLS 실수의 영향 | **즉시 데이터 노출** | 노출까지 한 단계 더 필요 |
| 접근 감사 로그 | 부분적으로만 가능 | 전 경로 기록 가능 |
| 사용량 측정 (과금 기준) | 어려움 | 용이 |
| 실시간 기능 | Supabase 기능 활용 가능 | 별도 설계 필요 |
| 데이터 저장소 교체 | 어려움 (앱까지 수정) | 용이 (백엔드만 수정) |
| 규칙의 단순함 | 경로마다 판단 필요 | **"앱은 백엔드만 호출한다"** 한 줄 |

---

## 결정

**나. 백엔드 단일 창구를 사용한다.**

**단, 인증은 예외로 한다.** 로그인·로그아웃·세션 갱신은 앱이 Supabase Auth 를 직접 사용한다.
이는 Supabase Auth 의 표준 사용 방식이며, 앱은 이때 얻은 토큰을 백엔드 호출에 첨부한다.

정리하면 다음과 같다.

| 대상 | 경로 |
|---|---|
| 로그인 / 로그아웃 / 세션 | 앱 → Supabase Auth (직접) |
| 대화, 기억, 관계, 결제, 설정 등 모든 데이터 | 앱 → 백엔드 → Supabase |

---

## 이유

1. **대화 데이터의 민감도가 높다.**
   Samantha 의 대화 기록은 사용자의 사적인 감정과 관계를 담는다.
   RLS 정책 하나의 실수가 곧바로 타인의 대화 노출로 이어지는 구조를 피한다.

2. **수익화 기준이 대화량이다.** (`docs/PRODUCT.md` 10장)
   사용량을 정확히 측정하려면 모든 요청이 한 지점을 통과해야 한다.

3. **관계 단계와 친밀도는 서버만 계산한다.** (`docs/ARCHITECTURE.md` 3장)
   앱이 데이터베이스를 직접 변경할 수 있으면 이 원칙이 무너진다.

4. **규칙이 단순하다.**
   "앱은 백엔드만 호출한다"는 한 줄이면 된다.
   하이브리드 방식은 기능마다 경로를 판단해야 하고, 그 판단 지점이 곧 실수가 나는 지점이다.

5. **운영 관점에서 통제 지점이 하나다.**
   접근 기록, 사용량 제한, 안전 정책, 장애 대응이 모두 한 곳에 모인다.

---

## 결과로 따라오는 것

- **백엔드 작업량이 늘어난다.** 목록 조회 하나에도 API 가 필요하다.
- 실시간 기능(예: 타이핑 표시)이 필요해지면 별도로 설계해야 한다.
- **RLS 는 여전히 모든 테이블에 적용한다.**
  앱에 `anon key` 가 존재하는 이상 기술적으로는 직접 접근이 가능하므로,
  RLS 를 2차 방어선으로 유지한다. RLS 없는 테이블을 만들지 않는다는 규칙은 그대로다.
- 앱은 오프라인 표시를 위해 로컬 캐시를 둘 수 있으나,
  캐시는 표시 용도로만 쓰고 **판단 근거로 삼지 않는다.**

---

## 되돌릴 때의 비용

**낮음.** 나 → 가 전환은 필요한 화면에 한해 직접 접근을 열어주면 된다.
반대 방향(가 → 나)이 훨씬 비싸다. 따라서 더 엄격한 쪽에서 시작한다.

## 아직 결정하지 않은 것

- 실시간 기능의 구현 방식
- 앱 로컬 캐시의 범위와 보관 기간
- 백엔드 API 의 구체적인 형태
