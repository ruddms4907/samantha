# DATABASE — 데이터베이스 설계

> 이 문서는 테이블 구조, 접근 통제, 변경 절차를 정의한다.
> 제품 정책은 `docs/PRODUCT.md`, 시스템 구조는 `docs/ARCHITECTURE.md` 를 따른다.

- 상태: **작성 중 (조각 1 완료)**
- 최종 수정: 2026-09-02

## 작성 진행 상황

| 조각 | 내용 | 상태 |
|---|---|---|

---

## 1. 기본 원칙

1. **모든 대화·기억·관계 데이터는 `사용자 × Companion` 단위에 귀속된다.**
   (`docs/PRODUCT.md` 4장) 이 원칙을 어기는 스키마는 잘못된 스키마다.
2. **RLS 없는 테이블을 만들지 않는다.** 예외 없다.
3. **필요 이상의 개인정보를 저장하지 않는다.** 저장하지 않은 정보는 유출될 수 없다.
4. **모든 변경은 마이그레이션 파일로 남긴다.** 대시보드에서 직접 고치지 않는다.
5. **국가와 시간대를 가정하지 않는다.** (`docs/ARCHITECTURE.md` 11장)

---

## 2. 명명 규칙

| 대상 | 규칙 | 예 |
|---|---|---|
| 테이블 | 소문자 + 밑줄, **복수형** | `users`, `companions`, `messages` |
| 컬럼 | 소문자 + 밑줄 | `display_name`, `relationship_stage` |
| 외래 키 | `<대상 테이블 단수>_id` | `user_id`, `companion_id` |
| 참/거짓 | `is_` 또는 `has_` 로 시작 | `is_active`, `has_consented` |
| 시각 | `_at` 으로 끝냄 | `created_at`, `last_message_at` |
| 인덱스 | `idx_<테이블>_<컬럼>` | `idx_messages_conversation_id` |

- **약어를 쓰지 않는다.** (`usr` ❌ / `user` ⭕)
- 대문자와 공백을 쓰지 않는다. PostgreSQL 에서 따옴표가 강제되어 다루기 어려워진다.

---

## 3. 공통 컬럼

모든 테이블은 다음 세 컬럼을 가진다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | `uuid` | 기본 키. 데이터베이스가 생성한다 |
| `created_at` | `timestamptz` | 생성 시각. 필수 |
| `updated_at` | `timestamptz` | 마지막 수정 시각. 변경 시 자동 갱신 |

- 기록만 쌓이고 수정되지 않는 로그성 테이블은 `updated_at` 을 생략할 수 있다.
- 생략할 경우 그 이유를 해당 테이블 설명에 적는다.

---

## 4. ID 형식 — UUID

**모든 기본 키는 `uuid` 를 사용한다.**

- 순차 숫자를 쓰지 않는다. 순차 ID 는 타인의 ID 를 추측할 수 있고,
  전체 가입자 수를 외부에 노출한다.
- Supabase Auth 의 사용자 ID 가 이미 `uuid` 이므로 일관성이 유지된다.
- 외부 노출용 별도 식별자를 따로 두지 않는다. UUID 자체가 추측 불가능하므로 불필요하다.

---

## 5. 시각 처리

- **모든 시각은 `timestamptz` 로 저장하고, 값은 UTC 로 다룬다.**
- 사용자에게 표시할 때만 사용자 시간대로 변환한다.
- 사용자 시간대는 계정 정보에 저장한다. (조각 2)
- **KST 를 코드나 스키마에 고정하지 않는다.**
- "날짜만" 필요한 경우에도 시간대 경계 문제가 생기므로 `timestamptz` 를 쓴다.

---

## 6. 삭제 정책

**기본은 실제 삭제(hard delete)다.**

- 데이터를 지우면 실제로 사라진다.
- 개인정보보호법상 사용자의 삭제 요구에 대응하려면 이 방식이 맞다.
- "삭제됨" 표시만 남기는 방식(soft delete)은 **예외적으로만** 쓴다.
  - 쓰는 경우 `deleted_at timestamptz` 컬럼을 두고,
  - **왜 예외인지 해당 테이블 설명에 반드시 적는다.**

### 참조 정리

- 삭제로 인해 참조가 깨지지 않도록, 모든 외래 키에 삭제 시 동작을 명시한다.
- 사용자가 삭제되면 그 사용자의 대화·기억·관계 데이터도 함께 삭제되는 것을 기본으로 한다.
- 감사 로그처럼 보존이 필요한 기록은 사용자 식별자와의 연결을 끊고 남긴다.
  구체적인 절차는 **조각 5** 에서 확정한다.

---

## 7. RLS 기본 방침

- **모든 테이블에 RLS 를 활성화한다. 예외 없다.**
- 기본 정책은 **전부 차단**이며, 필요한 접근만 명시적으로 허용한다.
  정책을 빠뜨렸을 때 데이터가 새는 대신 막히도록 한다.
- **새 테이블을 만드는 마이그레이션에 RLS 활성화와 정책을 함께 포함한다.**
  나중에 따로 추가하지 않는다.
- 백엔드는 `service_role` 로 접근하므로 RLS 를 우회한다.
  따라서 실제 접근 통제의 1차 책임은 백엔드 코드에 있고,
  **RLS 는 2차 방어선**이다. (`docs/DECISIONS/0002`)
- 운영 편의를 이유로 RLS 를 끄지 않는다.

---

## 8. 마이그레이션 규칙

- 위치: `supabase/migrations/`
- 파일명: `<타임스탬프>_<설명>.sql` (Supabase CLI 형식)
- **모든 마이그레이션 파일은 Git 에 커밋한다.**

### 규칙

1. **이미 적용된 마이그레이션 파일을 수정하지 않는다.** 변경이 필요하면 새 파일을 추가한다.
2. 적용 순서는 항상 **Development → Staging → Production** 이다.
3. 되돌려야 할 경우, 되돌리는 마이그레이션을 새로 만든다.
4. 컬럼 삭제, 타입 변경 등 **되돌릴 수 없는 변경은 적용 전에 별도로 검토한다.**
5. **Supabase 대시보드에서 스키마를 직접 수정하지 않는다.**
   대시보드에서 바꾼 내용은 다른 환경과 다른 개발자에게 전달되지 않는다.

---

## 9. 금지 사항

- 비밀번호를 직접 저장하지 않는다. 인증은 Supabase Auth 가 담당한다.
- 필요 이상의 개인정보를 저장하지 않는다.
- **대화·기억·관계 테이블을 `companion_id` 없이 만들지 않는다.** (1장)
- 두 Companion 의 데이터가 섞일 수 있는 경로를 만들지 않는다.
- 운영 편의를 위해 RLS 를 끄거나 정책을 넓게 열지 않는다.

---

## 10. 계정 영역

### 10.1 Supabase Auth 와의 역할 분담

로그인에 필요한 정보는 Supabase Auth 가 관리한다. **우리가 만들지 않는다.**

| 구분 | 보관 주체 | 내용 |
|---|---|---|
| 인증 정보 | Supabase Auth (`auth.users`) | 이메일, 비밀번호(암호화), 세션 |
| 프로필 정보 | 우리 테이블 (`user_profiles`) | 닉네임, 언어, 시간대, 국가, 계정 상태 |

- **이메일을 우리 테이블에 중복 저장하지 않는다.**
  두 곳에 두면 한쪽만 갱신되는 사고가 나고, 개인정보 노출면이 하나 더 늘어난다.
- 이메일이 필요하면 `auth.users` 에서 조회한다.

---

### 10.2 `user_profiles`

사용자 한 명당 한 행. `auth.users` 와 1:1 로 대응한다.

| 컬럼 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `id` | `uuid` | ✔ | 기본 키. `auth.users.id` 를 참조한다. 계정 삭제 시 함께 삭제 |
| `display_name` | `text` | ✔ | 닉네임. Companion 이 사용자를 부르는 이름 |
| `locale` | `text` | ✔ | 언어. 예: `ko` |
| `timezone` | `text` | ✔ | IANA 시간대. 예: `Asia/Seoul` |
| `country` | `text` | ✔ | ISO 3166-1 alpha-2. 예: `KR` |
| `status` | `text` | ✔ | `active` / `suspended` / `deletion_pending` |
| `adult_verified_at` | `timestamptz` | ✔ | 만 18세 확인을 완료한 시각 |
| `created_at` | `timestamptz` | ✔ | 공통 컬럼 |
| `updated_at` | `timestamptz` | ✔ | 공통 컬럼 |

**규칙**

- **생년월일을 저장하지 않는다.**
  가입 시 생년월일을 입력받아 만 18세 이상인지 확인하고, **확인했다는 사실만** 남긴다.
  저장하지 않은 정보는 유출될 수 없다. (1장 3번 원칙)
- `adult_verified_at` 이 비어 있는 계정은 서비스를 이용할 수 없다.
- `locale` / `timezone` / `country` 의 기본값은 컬럼 기본값으로만 둔다.
  **코드에 `ko` 나 `Asia/Seoul` 을 고정하지 않는다.** (`ARCHITECTURE.md` 11장)
- `status` 의 의미
  | 값 | 뜻 |
  |---|---|
  | `active` | 정상 이용 |
  | `suspended` | 운영자에 의한 제재 |
  | `deletion_pending` | 삭제 요청 접수됨 (절차는 조각 5) |

---

### 10.3 `user_consents`

약관 동의 이력. **누가 언제 어느 버전에 동의했는지**를 남긴다.

| 컬럼 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `id` | `uuid` | ✔ | 기본 키 |
| `user_id` | `uuid` | ✔ | `user_profiles.id` 참조 |
| `consent_type` | `text` | ✔ | `terms` / `privacy` / `age` / `marketing` |
| `document_version` | `text` | ✔ | 동의한 문서의 버전. 예: `v1.0` |
| `is_agreed` | `boolean` | ✔ | 동의 `true` / 철회 `false` |
| `agreed_at` | `timestamptz` | ✔ | 행위 시각 |
| `created_at` | `timestamptz` | ✔ | 공통 컬럼 |

**규칙**

- **이 테이블은 덮어쓰지 않는다. 행을 계속 추가한다.**
  동의를 철회하면 `is_agreed = false` 행을 새로 남긴다.
  덮어쓰면 "언제 어느 버전에 동의했는지"를 증명할 수 없게 된다.
- 현재 동의 상태는 `(user_id, consent_type)` 별 **가장 최근 행**으로 판단한다.
- **IP 주소를 저장하지 않는다.**
  로그인된 계정의 행위 기록만으로 증빙에 충분하며, 수집하지 않는 편이 관리 부담이 작다.
- 약관 문서의 버전이 바뀌면 재동의를 받고 새 행을 남긴다.
- 수정되지 않는 기록성 테이블이므로 `updated_at` 을 두지 않는다. (3장 예외)

---

### 10.4 접근 통제

- 두 테이블 모두 RLS 를 활성화하고 **기본은 전부 차단**한다. (7장)
- 앱은 데이터베이스에 직접 접근하지 않으므로, **앱을 위한 허용 정책을 만들지 않는다.**
  (`docs/DECISIONS/0002`)
- 백엔드만 `service_role` 로 접근한다.

## 11. Companion 영역

### 11.1 격리 구조

두 Companion 의 데이터가 섞이지 않게 하는 방법은 **코드의 주의가 아니라 구조**다.

```
user_profiles
     │
     ├──► user_companions  (사용자 A × 남성)   ← 하나의 "관계"
     │           ▲
     │           └── 대화 · 기억 · 관계 이력이 전부 여기에 붙는다
     │
     └──► user_companions  (사용자 A × 여성)   ← 완전히 다른 "관계"
                 ▲
                 └── 위와 공유되는 데이터가 하나도 없다
```

- **대화와 기억 테이블은 `user_id` 를 직접 갖지 않는다. `user_companion_id` 만 갖는다.**
- 따라서 "사용자의 모든 대화"를 Companion 구분 없이 조회하는 것이 **구조적으로 불가능하다.**
- 두 Companion 의 데이터를 합치는 뷰나 함수를 만들지 않는다.

---

### 11.2 `companion_templates`

Companion 의 원본 정의. **전체에 2행만 존재한다.** (남성 1, 여성 1)
사용자별로 복제하지 않는다.

| 컬럼 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `id` | `uuid` | ✔ | 기본 키 |
| `gender` | `text` | ✔ | `male` / `female` |
| `base_persona` | `text` | ✔ | 기본 성격 정의. AI 프롬프트의 재료 |
| `is_enabled` | `boolean` | ✔ | 신규 활성화 허용 여부 |
| `created_at` / `updated_at` | `timestamptz` | ✔ | 공통 컬럼 |

**규칙**

- **`base_persona` 를 코드에 두지 않는다.** 이 테이블에 둔다.
  (`ARCHITECTURE.md` 5장 — 운영 데이터와 코드의 분리)
  코드에 두면 문구 하나 고치는 데 앱 심사를 다시 받아야 한다.
- 값 변경은 운영자만 할 수 있으며, 변경 이력은 감사 로그로 남긴다. (조각 5)
- `is_enabled = false` 는 **신규 활성화만 막는다.**
  이미 존재하는 관계 데이터는 그대로 보존한다.

---

### 11.3 `user_companions` — 이 설계의 중심

사용자 한 명당 **2행**(남/여)이 생긴다.
**대화·기억·관계 이력은 모두 이 테이블의 `id` 를 참조한다.**

| 컬럼 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `id` | `uuid` | ✔ | 기본 키. **모든 대화·기억이 이 값을 참조한다** |
| `user_id` | `uuid` | ✔ | `user_profiles.id` 참조 |
| `template_id` | `uuid` | ✔ | `companion_templates.id` 참조 |
| `companion_name` | `text` | ✔ | 사용자가 지은 이름 |
| `is_active` | `boolean` | ✔ | 활성 여부. **계정당 1개만 `true`** |
| `relationship_stage` | `smallint` | ✔ | 1 낯섦 ~ 5 깊은 관계 |
| `intimacy_score` | `integer` | ✔ | 내부 친밀도. **사용자에게 노출하지 않는다** |
| `stage_changed_at` | `timestamptz` | | 마지막 단계 변경 시각 |
| `total_interaction_days` | `integer` | ✔ | 대화한 날짜의 수 (연속일이 아님) |
| `last_interacted_at` | `timestamptz` | | 마지막 대화 시각 |
| `activated_at` | `timestamptz` | | 마지막으로 활성화된 시각 |
| `created_at` / `updated_at` | `timestamptz` | ✔ | 공통 컬럼 |

**데이터베이스 제약 (사람의 주의력에 의존하지 않는다)**

| 제약 | 목적 |
|---|---|
| `(user_id, template_id)` 유일 | 같은 Companion 이 두 개 생기지 않게 |
| `user_id` 부분 유니크 (`is_active = true` 인 행만) | **계정당 활성 Companion 을 1명으로 강제** |
| `relationship_stage` 는 1~5 | 잘못된 단계 값 차단 |
| 사용자 삭제 시 함께 삭제 | 계정 삭제 시 관계 데이터가 남지 않게 |

두 번째 제약이 핵심이다. 백엔드 코드에 실수가 있어도 **데이터베이스가 거부한다.**

**규칙**

- **`companion_name` 은 사용자가 입력한다.** 부적절한 이름의 처리는 `docs/SAFETY.md` 에서 정한다.
- **`intimacy_score` 는 앱 응답에 포함하지 않는다.** 사용자는 말투와 태도의 변화로만 관계를 인지한다.
- `relationship_stage` 와 `intimacy_score` 는 **백엔드만 변경한다.** 앱이 보낸 값을 신뢰하지 않는다.
- 비활성 기간은 관계 후퇴 판정에 반영하지 않는다. (`PRODUCT.md` 4.4)
  판정 시 `last_interacted_at` 과 `activated_at` 을 함께 본다.
- `total_interaction_days` 는 **대화한 날짜의 수**다. 연속 접속일이 아니다.
  관계 상승의 "지속성" 판정에 쓴다. (`PRODUCT.md` 5.1)

---

### 11.4 `relationship_events`

관계 단계가 바뀔 때마다 행을 추가한다. **덮어쓰지 않는다.**

| 컬럼 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `id` | `uuid` | ✔ | 기본 키 |
| `user_companion_id` | `uuid` | ✔ | 어느 관계에서 일어난 일인지 |
| `from_stage` | `smallint` | ✔ | 변경 전 단계 |
| `to_stage` | `smallint` | ✔ | 변경 후 단계 |
| `trigger` | `text` | ✔ | `user_choice` / `system` |
| `occurred_at` | `timestamptz` | ✔ | 발생 시각 |
| `created_at` | `timestamptz` | ✔ | 공통 컬럼 |

**규칙**

- **3단계 → 4단계(썸 → 연인) 변경은 `trigger` 가 반드시 `user_choice` 여야 한다.**
  AI 가 사용자 동의 없이 관계를 진전시키지 않는다. (`PRODUCT.md` 5.1)
- 수정되지 않는 기록성 테이블이므로 `updated_at` 을 두지 않는다. (3장 예외)
- 이 기록으로 "언제 어떻게 관계가 바뀌었는지"를 사후에 확인할 수 있다.

---

### 11.5 접근 통제

- 세 테이블 모두 RLS 활성화, **기본 전부 차단**. (7장)
- 앱을 위한 허용 정책을 만들지 않는다. 백엔드만 `service_role` 로 접근한다.

| 항목 | 다루는 곳 |
|---|---|
| 관계 단계에 따라 성격과 말투가 어떻게 변하는지 | `docs/AI_SYSTEM.md` |
| 친밀도 계산식, 단계 상승 조건의 구체적 기준 | `docs/AI_SYSTEM.md` |
| Companion 이름의 부적절 입력 처리 | `docs/SAFETY.md` |
| 대화와 기억 테이블 | 조각 4 |

## 12. 대화와 기억 영역

### 12.1 원문과 기억을 분리한다

```
대화 원문   "아 진짜 내일 발표 너무 떨려... 팀장님이 계속 쪼아대서..."
                              │ 추출
                              ▼
기억        "발표를 앞두고 있음. 팀장과의 관계로 스트레스"
```

- **원문은 12개월 보관 후 삭제한다.**
- **기억은 계정이 유지되는 동안 보존한다.**

원문은 시간이 지나면 다시 읽을 일이 거의 없으면서, 가장 민감하고 용량이 크다.
Companion 이 관계를 이어가는 데 필요한 것은 추출된 기억이다.
사람도 6개월 전 대화의 문장은 잊지만 상대가 어떤 사람인지는 안다.

> 보관 기간은 **개인정보처리방침에 반드시 명시한다.** (조각 5 / `docs/PRIVACY.md`)

---

### 12.2 `conversations`

대화 묶음. 일정 시간 공백이 생기면 새 대화로 구분한다.

| 컬럼 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `id` | `uuid` | ✔ | 기본 키 |
| `user_companion_id` | `uuid` | ✔ | `user_companions.id` 참조 |
| `started_at` | `timestamptz` | ✔ | 대화 시작 시각 |
| `last_message_at` | `timestamptz` | ✔ | 마지막 메시지 시각 |
| `message_count` | `integer` | ✔ | 메시지 수 |
| `is_summarized` | `boolean` | ✔ | 기억 추출 완료 여부 |
| `created_at` / `updated_at` | `timestamptz` | ✔ | 공통 컬럼 |

**규칙**

- **`user_id` 를 두지 않는다.** `user_companion_id` 만 참조한다. (11.1)
- 새 대화로 나누는 기준(공백 시간)은 **운영 설정에 둔다.** 코드에 고정하지 않는다. (조각 5)
- `is_summarized` 가 `false` 인 대화의 원문은 삭제하지 않는다. (12.5)

---

### 12.3 `messages`

| 컬럼 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `id` | `uuid` | ✔ | 기본 키 |
| `conversation_id` | `uuid` | ✔ | `conversations.id` 참조 |
| `role` | `text` | ✔ | `user` / `companion` |
| `content` | `text` | ✔ | 메시지 내용 |
| `token_count` | `integer` | ✔ | 사용량 측정용 (`PRODUCT.md` 10장) |
| `created_at` | `timestamptz` | ✔ | 공통 컬럼 |

**규칙**

- **메시지는 수정하지 않는다.** 따라서 `updated_at` 을 두지 않는다. (3장 예외)
- `content` 는 이 서비스에서 가장 민감한 데이터다. 취급 기준은 `docs/SECURITY.md` 를 따른다.
- `token_count` 는 수익화 기준이 대화량이므로 **저장 시점에 함께 기록한다.**
  나중에 다시 계산하려 하면 정확도가 떨어진다.

---

### 12.4 `memories`

| 컬럼 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `id` | `uuid` | ✔ | 기본 키 |
| `user_companion_id` | `uuid` | ✔ | 어느 관계의 기억인지 |
| `content` | `text` | ✔ | 기억 내용 |
| `memory_type` | `text` | ✔ | `fact` / `preference` / `event` / `emotion` / `relationship` |
| `importance` | `smallint` | ✔ | 1~5 |
| `source_conversation_id` | `uuid` | | 어느 대화에서 나왔는지. **원문 삭제 시 비워질 수 있다** |
| `occurred_at` | `timestamptz` | | 실제로 있었던 일의 시점 (대화 시점과 다를 수 있음) |
| `last_recalled_at` | `timestamptz` | | 마지막으로 꺼낸 시각 |
| `recall_count` | `integer` | ✔ | 꺼낸 횟수 |
| `is_active` | `boolean` | ✔ | 유효 여부 |
| `created_at` / `updated_at` | `timestamptz` | ✔ | 공통 컬럼 |

**규칙**

- **기억은 원문에 의존하지 않는다.** 원문이 삭제되어도 기억은 그대로 남는다.
- **사실이 바뀌면 기존 기억을 고치지 않는다.**
  기존 기억을 `is_active = false` 로 두고 새 기억을 추가한다.
  그래야 "예전엔 그랬는데 지금은 달라졌구나" 를 표현할 수 있다.
- 두 Companion 의 기억이 섞이지 않도록 반드시 `user_companion_id` 를 통해서만 조회한다.
- **기억을 찾아오는 방식(검색 방법, Vector DB 사용 여부)은 Phase 5 에서 결정한다.**
  필요한 컬럼은 그때 마이그레이션으로 추가한다.

---

### 12.5 보관 기간

| 데이터 | 보관 기간 | 비고 |
|---|---|---|
| `messages` (대화 원문) | **12개월** | 이후 자동 삭제 |
| `conversations` | 12개월 | 원문과 함께 삭제 |
| `memories` (기억) | **계정 유지 기간 동안** | 계정 삭제 시 함께 삭제 |

**규칙**

- 삭제는 백엔드의 정기 작업으로 수행한다. (`ARCHITECTURE.md` 3.2)
- **기억 추출이 끝나지 않은 대화(`is_summarized = false`)의 원문은 삭제하지 않는다.**
- 12개월이라는 값은 **운영 설정에 둔다.** 다만 기간을 바꾸려면
  개인정보처리방침 고지가 함께 필요하므로 임의로 변경하지 않는다.
- 사용자가 계정을 삭제하면 원문과 기억을 모두 삭제한다. 절차는 조각 5 에서 정한다.

---

### 12.6 접근 통제

- 세 테이블 모두 RLS 활성화, **기본 전부 차단**. 백엔드만 접근한다.
- **운영자도 대화 원문을 일상적으로 열람하지 않는다.** (`ARCHITECTURE.md` 3.4)
  열람이 필요한 경우 사유를 남기고 감사 로그에 기록한다. (조각 5)

---

### 12.7 저장 시 보호

- Supabase 는 저장된 데이터를 기본적으로 암호화한다.
- **애플리케이션 단계의 추가 암호화는 도입하지 않는다.**
  대화 내용을 암호화하면 기억 추출과 검색이 불가능해지고, 키 분실 시 복구도 불가능하다.
  필요하다고 판단되면 별도 결정 문서로 다룬다.

---

| 기억 검색 방식 / Vector DB 사용 여부 | Phase 5 |
| 사용량 집계와 과금 처리 | 조각 5 / Phase 7 |
