# DATABASE — 데이터베이스 설계

> 이 문서는 테이블 구조, 접근 통제, 변경 절차를 정의한다.
> 제품 정책은 `docs/PRODUCT.md`, 시스템 구조는 `docs/ARCHITECTURE.md` 를 따른다.

- 상태: **작성 중 (조각 1 완료)**
- 최종 수정: 2026-09-02

## 작성 진행 상황

| 조각 | 내용 | 상태 |
|---|---|---|
| 1 | 기본 규칙 (이 문서의 2~9장) | ✅ 완료 |
| 2 | 계정 영역 | ⬜ 예정 |
| 3 | Companion 영역 | ⬜ 예정 |
| 4 | 대화와 기억 | ⬜ 예정 |
| 5 | 운영 영역 및 삭제 정책 | ⬜ 예정 |

> 이 문서는 **설계도**다. 실제 SQL 은 Phase 3 에서 `supabase/migrations/` 에 작성한다.

---

## 1. 기본 원칙

1. **모든 대화·기억·관계 데이터는 `사용자 × Companion` 단위에 귀속된다.**
   (`docs/PRODUCT.md` 4장) 이 원칙을 어기는 스키마는 잘못된 스키마다.
2. **RLS 없는 테이블을 만들지 않는다.** 예외 없다.
3. **필요 이상의 개인정보를 저장하지 않는다.** 저장하지 않은 정보는 유출될 수 없다.
4. **모든 변경은 마이그레이션 파일로 남긴다.** 대시보드에서 직접 고치지 않는다.
5. **국가와 시간대를 가정하지 않는다.** (`docs/ARCHITECTURE.md` 11장)

---

## 2. 명명 규칙

| 대상 | 규칙 | 예 |
|---|---|---|
| 테이블 | 소문자 + 밑줄, **복수형** | `users`, `companions`, `messages` |
| 컬럼 | 소문자 + 밑줄 | `display_name`, `relationship_stage` |
| 외래 키 | `<대상 테이블 단수>_id` | `user_id`, `companion_id` |
| 참/거짓 | `is_` 또는 `has_` 로 시작 | `is_active`, `has_consented` |
| 시각 | `_at` 으로 끝냄 | `created_at`, `last_message_at` |
| 인덱스 | `idx_<테이블>_<컬럼>` | `idx_messages_conversation_id` |

- **약어를 쓰지 않는다.** (`usr` ❌ / `user` ⭕)
- 대문자와 공백을 쓰지 않는다. PostgreSQL 에서 따옴표가 강제되어 다루기 어려워진다.

---

## 3. 공통 컬럼

모든 테이블은 다음 세 컬럼을 가진다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | `uuid` | 기본 키. 데이터베이스가 생성한다 |
| `created_at` | `timestamptz` | 생성 시각. 필수 |
| `updated_at` | `timestamptz` | 마지막 수정 시각. 변경 시 자동 갱신 |

- 기록만 쌓이고 수정되지 않는 로그성 테이블은 `updated_at` 을 생략할 수 있다.
- 생략할 경우 그 이유를 해당 테이블 설명에 적는다.

---

## 4. ID 형식 — UUID

**모든 기본 키는 `uuid` 를 사용한다.**

- 순차 숫자를 쓰지 않는다. 순차 ID 는 타인의 ID 를 추측할 수 있고,
  전체 가입자 수를 외부에 노출한다.
- Supabase Auth 의 사용자 ID 가 이미 `uuid` 이므로 일관성이 유지된다.
- 외부 노출용 별도 식별자를 따로 두지 않는다. UUID 자체가 추측 불가능하므로 불필요하다.

---

## 5. 시각 처리

- **모든 시각은 `timestamptz` 로 저장하고, 값은 UTC 로 다룬다.**
- 사용자에게 표시할 때만 사용자 시간대로 변환한다.
- 사용자 시간대는 계정 정보에 저장한다. (조각 2)
- **KST 를 코드나 스키마에 고정하지 않는다.**
- "날짜만" 필요한 경우에도 시간대 경계 문제가 생기므로 `timestamptz` 를 쓴다.

---

## 6. 삭제 정책

**기본은 실제 삭제(hard delete)다.**

- 데이터를 지우면 실제로 사라진다.
- 개인정보보호법상 사용자의 삭제 요구에 대응하려면 이 방식이 맞다.
- "삭제됨" 표시만 남기는 방식(soft delete)은 **예외적으로만** 쓴다.
  - 쓰는 경우 `deleted_at timestamptz` 컬럼을 두고,
  - **왜 예외인지 해당 테이블 설명에 반드시 적는다.**

### 참조 정리

- 삭제로 인해 참조가 깨지지 않도록, 모든 외래 키에 삭제 시 동작을 명시한다.
- 사용자가 삭제되면 그 사용자의 대화·기억·관계 데이터도 함께 삭제되는 것을 기본으로 한다.
- 감사 로그처럼 보존이 필요한 기록은 사용자 식별자와의 연결을 끊고 남긴다.
  구체적인 절차는 **조각 5** 에서 확정한다.

---

## 7. RLS 기본 방침

- **모든 테이블에 RLS 를 활성화한다. 예외 없다.**
- 기본 정책은 **전부 차단**이며, 필요한 접근만 명시적으로 허용한다.
  정책을 빠뜨렸을 때 데이터가 새는 대신 막히도록 한다.
- **새 테이블을 만드는 마이그레이션에 RLS 활성화와 정책을 함께 포함한다.**
  나중에 따로 추가하지 않는다.
- 백엔드는 `service_role` 로 접근하므로 RLS 를 우회한다.
  따라서 실제 접근 통제의 1차 책임은 백엔드 코드에 있고,
  **RLS 는 2차 방어선**이다. (`docs/DECISIONS/0002`)
- 운영 편의를 이유로 RLS 를 끄지 않는다.

---

## 8. 마이그레이션 규칙

- 위치: `supabase/migrations/`
- 파일명: `<타임스탬프>_<설명>.sql` (Supabase CLI 형식)
- **모든 마이그레이션 파일은 Git 에 커밋한다.**

### 규칙

1. **이미 적용된 마이그레이션 파일을 수정하지 않는다.** 변경이 필요하면 새 파일을 추가한다.
2. 적용 순서는 항상 **Development → Staging → Production** 이다.
3. 되돌려야 할 경우, 되돌리는 마이그레이션을 새로 만든다.
4. 컬럼 삭제, 타입 변경 등 **되돌릴 수 없는 변경은 적용 전에 별도로 검토한다.**
5. **Supabase 대시보드에서 스키마를 직접 수정하지 않는다.**
   대시보드에서 바꾼 내용은 다른 환경과 다른 개발자에게 전달되지 않는다.

---

## 9. 금지 사항

- 비밀번호를 직접 저장하지 않는다. 인증은 Supabase Auth 가 담당한다.
- 필요 이상의 개인정보를 저장하지 않는다.
- **대화·기억·관계 테이블을 `companion_id` 없이 만들지 않는다.** (1장)
- 두 Companion 의 데이터가 섞일 수 있는 경로를 만들지 않는다.
- 운영 편의를 위해 RLS 를 끄거나 정책을 넓게 열지 않는다.
