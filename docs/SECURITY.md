# SECURITY — 보안 규칙

> 이 문서는 **무엇을 어디에 두고, 무엇을 절대 하지 않는가**를 정의한다.
> 새 기능을 만들 때는 10장의 체크리스트를 먼저 확인한다.

- 상태: 초안 (Phase 1)
- 최종 수정: 2026-09-02

---

## 1. 전제

**모바일 앱은 신뢰할 수 없는 환경이다.**

앱은 사용자 기기에 설치된다. 앱에 포함된 값은 어떤 방식으로 숨기더라도 추출할 수 있고,
앱이 서버로 보내는 값은 조작할 수 있다.

따라서 다음 두 문장이 모든 보안 규칙의 출발점이다.

1. **비밀 정보는 앱에 두지 않는다.**
2. **앱이 보낸 값을 믿지 않는다.**

---

## 2. 무엇을 지키는가

| 자산 | 유출 시 피해 |
|---|---|
| 사용자의 대화 내용 | **가장 심각.** 사적인 감정과 관계가 노출된다 |
| 사용자 계정 정보 | 계정 탈취, 사칭 |
| AI Provider API Key | 금전적 피해. 타인이 우리 계정으로 AI 를 사용 |
| Supabase `service_role` 키 | **전체 데이터베이스 접근.** 사실상 모든 것 |
| 결제 검증 자격 증명 | 부정 결제, 구독 우회 |

---

## 3. 비밀 정보 관리

### 3.1 무엇이 어디에 있어야 하는가

| 자산 | 위치 | 앱에 둬도 되나 | Git 커밋 |
|---|---|---|---|
| Supabase URL | 앱 / 백엔드 | 가능 | 가능 |
| Supabase `anon` key | 앱 / 백엔드 | 가능 (RLS 로 보호) | 가능 |
| Supabase `service_role` key | **백엔드만** | **불가** | **금지** |
| AI Provider API Key | **백엔드만** | **불가** | **금지** |
| 푸시 발송 자격 증명 | **백엔드만** | **불가** | **금지** |
| 인앱결제 검증 자격 증명 | **백엔드만** | **불가** | **금지** |
| 앱 서명 키 (`.p8`, `.keystore`) | 로컬 / 빌드 서비스 | — | **금지** |
| 사용자 인증 토큰(JWT) | 앱 (기기 보안 저장소) | 가능 | — |

### 3.2 규칙

- **실제 키 값은 `.env` 에 두고, `.env` 는 커밋하지 않는다.** (`.gitignore` 로 차단됨)
- `.env.example` 에는 **키의 이름만** 적는다. 값은 절대 적지 않는다.
- 개발 / Staging / Production 은 **서로 다른 키를 사용한다.**
- 키를 채팅, 메모, 스크린샷, 이슈, 커밋 메시지에 붙여넣지 않는다.
- 백엔드는 키를 **환경변수로만** 읽는다. 코드에 기본값으로 넣지 않는다.

### 3.3 키가 노출되었을 때

> **Git 에 한 번 올라간 값은 파일을 지워도 이력에 남는다.**
> "지웠으니 괜찮다"는 성립하지 않는다.

```
1. 해당 키를 즉시 폐기(revoke)한다      ← 가장 먼저
2. 새 키를 발급하고 교체한다
3. 그 키로 이루어진 사용 내역을 확인한다
4. 필요하면 이력에서 제거한다 (하지만 1번이 우선)
```

당황해서 순서를 바꾸지 않는다. **폐기가 먼저다.**

## 4. 인증과 권한

### 4.1 사용자

- 인증은 Supabase Auth 가 담당한다. **비밀번호를 직접 저장하지 않는다.**
- 백엔드는 **모든 요청에서 토큰을 검증한다.** 예외 경로를 만들지 않는다.
- **요청 본문에 담긴 사용자 식별자를 신뢰하지 않는다.** 토큰에서 추출한 값만 사용한다.
- 관계 단계, 친밀도, 구독 상태 등 핵심 상태는 **서버만 변경한다.**

### 4.2 운영자

- 운영자 계정은 사용자 계정과 **완전히 분리한다.** (`DATABASE.md` 13.2)
- 최소 권한 원칙. `owner` 는 최소 인원으로 유지한다.
- **운영자의 조회·변경 행위는 감사 로그에 남긴다.** (`DATABASE.md` 13.3)
- 대화 원문 열람은 신고 건에 한하며 사유가 필수다. (`DATABASE.md` 13.7)

### 4.3 접근 통제

- **RLS 없는 테이블을 만들지 않는다.** 기본은 전부 차단. (`DATABASE.md` 7장)
- 앱은 데이터베이스에 직접 접근하지 않는다. (`DECISIONS/0002`)
  RLS 는 그럼에도 **2차 방어선**으로 유지한다.

---

## 5. 데이터 보호

- 모든 통신은 HTTPS 로만 한다.
- **필요 이상의 개인정보를 수집하지 않는다.**
  생년월일과 IP 를 저장하지 않기로 한 것이 그 적용이다. (`DATABASE.md` 10장)
- 대화 원문은 12개월 후 삭제한다. (`DATABASE.md` 12.5)
- 계정 삭제 시 7일 유예 후 완전 삭제한다. (`DATABASE.md` 13.6)
- **Production 데이터를 개발이나 Staging 으로 복사하지 않는다.**
- 데이터베이스 백업 정책은 아직 정하지 않았다. (11장)

---

## 6. 백엔드 규칙

- 모든 입력을 검증한다. **길이, 형식, 범위를 모두 확인한다.**
- **사용량 제한을 적용한다.** 무제한 호출은 곧 비용이다.
- 안전 정책 검사는 입력과 출력 양쪽에서 수행한다. (`SAFETY.md` 10장)
- 오류 응답에 내부 정보를 담지 않는다.
  스택 추적, 쿼리문, 파일 경로를 사용자에게 보내지 않는다.
- 특정 호스팅에만 있는 기능에 의존하지 않는다. (`DECISIONS/0001`)

### 로그 규칙

| 남긴다 | 남기지 않는다 |
|---|---|
| 요청 시각, 경로, 처리 시간 | **대화 내용** |
| 사용자 식별자 (UUID) | 이메일, 닉네임 |
| 오류 종류와 코드 | **토큰, 키, 비밀번호** |
| 사용량 수치 | 위기 상황 대화의 원문 (`SAFETY.md` 5.4) |

---

## 7. 모바일 앱 규칙

- 인증 토큰은 **기기의 보안 저장소**에 보관한다. 일반 저장소에 두지 않는다.
- 로그에 토큰이나 대화 내용을 출력하지 않는다. **운영 빌드에서는 디버그 로그를 끈다.**
- 로컬 캐시는 표시 용도로만 쓰고 **판단 근거로 삼지 않는다.** (`DECISIONS/0002`)
- 앱에서 안전 검사를 수행하지 않는다. 우회할 수 있기 때문이다.

---

## 8. 계정과 도구 보안

- GitHub 계정에 **2단계 인증을 적용한다.** 백업 코드는 별도로 보관한다.
- SSH 키는 기기마다 따로 만든다. **비밀키를 클라우드에 백업하지 않는다.**
- 기기를 분실하면 해당 키를 GitHub 에서 삭제한다. 그것으로 접근이 차단된다.
- Supabase, AI Provider, 스토어 개발자 계정에도 2단계 인증을 적용한다.

---

## 9. 의존성 관리

- **필요하지 않은 라이브러리를 추가하지 않는다.** 라이브러리 하나가 공격면 하나다.
- 추가할 때는 이유를 남긴다. (`CLAUDE.md`)
- 알려진 취약점을 정기적으로 점검한다.
- 검증되지 않은 출처의 패키지를 설치하지 않는다.

---

## 10. 체크리스트 — 새 기능을 만들 때

새로운 API, 테이블, 화면을 만들기 전에 확인한다.

- [ ] 새 테이블에 **RLS 를 켰고, 정책을 같은 마이그레이션에 포함**했는가
- [ ] 대화·기억·관계 데이터라면 **`user_companion_id` 를 통해서만** 접근하는가
- [ ] 비밀 정보가 앱 쪽으로 넘어가지 않는가
- [ ] 요청자의 신원을 **토큰에서** 확인하는가 (요청 본문이 아니라)
- [ ] 입력값의 길이·형식·범위를 검증하는가
- [ ] 사용량 제한이 걸려 있는가
- [ ] 오류 응답에 내부 정보가 없는가
- [ ] 로그에 대화 내용이나 개인정보가 남지 않는가
- [ ] 개인정보를 새로 수집한다면, **정말 필요한가**
- [ ] 운영자가 접근할 수 있는 기능이라면 **감사 로그를 남기는가**
