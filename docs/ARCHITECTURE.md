# ARCHITECTURE — Samantha 시스템 구조

> 이 문서는 "어떻게 만드는가"를 정의한다.
> "무엇을 만드는가"는 `docs/PRODUCT.md` 를 따른다. 두 문서가 충돌하면 PRODUCT.md 가 우선한다.

- 상태: 초안 (Phase 1)
- 최종 수정: 2026-09-02

---

## 1. 전제

Samantha는 대한민국 App Store / Google Play 에 정식 출시하고,
유료 사용자를 받아 수익화하며, 향후 해외 시장으로 확장하는 **상용 서비스**다.

따라서 이 문서는 프로토타입 기준이 아니라 **실제 운영 가능한 서비스 기준**으로 작성한다.

### 1.1 설계 원칙

1. **비밀 정보는 서버에만 존재한다.** 모바일 앱은 신뢰할 수 없는 환경으로 취급한다.
2. **데이터는 `User × Companion` 단위로 격리한다.** (`docs/PRODUCT.md` 4장)
3. **하나의 잘 구조화된 백엔드로 시작한다.**
   초기부터 마이크로서비스로 쪼개지 않는다. 다만 나중에 일부 기능을 분리할 수 있도록
   내부를 역할 단위로 나눠 둔다.
4. **과잉 설계를 하지 않는다.** 현재 필요하지 않은 대규모 트래픽 대비 구조를 미리 만들지 않는다.
5. **확장을 막는 구조를 만들지 않는다.** 특히 언어, 시간대, 국가에 대한 가정을 코드에 심지 않는다.
6. **환경을 분리한다.** 개발 / Staging / Production 은 데이터와 키를 공유하지 않는다.

## 2. 시스템 구성

```
┌──────────────────────────┐   ┌──────────────────────────┐
│       Mobile App         │   │   Admin Console (Web)    │
│  React Native + Expo(TS) │   │   운영자 전용 (미구현)      │
│  iOS / Android           │   │                          │
│  — 사용자용               │   │  — 운영자용               │
└─────────────┬────────────┘   └────────────┬─────────────┘
              │ HTTPS                       │ HTTPS
              └──────────────┬──────────────┘
                             ▼
              ┌──────────────────────────────┐
              │     Samantha Backend         │
              │   (독립 백엔드 애플리케이션)     │
              │                              │
              │  · AI 대화 처리                │
              │  · 장기 기억 처리              │
              │  · 관계 엔진                   │
              │  · 결제 영수증 검증             │
              │  · 푸시 알림 발송              │
              │  · 사용량 제한                 │
              │  · 안전 정책 적용              │
              │  · 운영 설정 제공 / 변경        │
              │  · 로깅 / 감사                 │
              │                              │
              │  ※ 모든 Secret 을 보관         │
              └───┬─────────┬─────────┬──────┘
                  │         │         │
                  ▼         ▼         ▼
            ┌────────┐┌────────┐┌──────────────┐
            │Supabase││   AI   ││  External    │
            │        ││Provider││  Services    │
            │Postgres││        ││              │
            │  Auth  ││ (미정)  ││ Push / IAP   │
            │  RLS   ││        ││ 검증 등 (미정) │
            └────────┘└────────┘└──────────────┘
```

**Admin Console 도 반드시 Backend 를 통해서만 데이터에 접근한다.**
Supabase 나 AI Provider 에 직접 연결하지 않는다.

확정된 구조는 다음과 같다.

```
Mobile App     ┐
               ├→ Samantha Backend → Supabase / AI Provider / External Services
Admin Console  ┘
```

Mobile App 과 Admin Console 은 서로 다른 사용자(사용자 / 운영자)를 위한 별개의 클라이언트이며,
인증 체계를 공유하지 않는다. 둘 다 데이터에는 Backend 를 통해서만 접근한다.

## 3. 계층별 책임

### 3.1 Mobile App

**한다**

- 화면 표시와 사용자 입력 처리
- Supabase Auth 를 통한 로그인 / 로그아웃 / 세션 유지 (**데이터 접근 중 유일한 직접 연결**)
- 백엔드 API 호출 (인증 토큰 첨부)
- 로컬 캐시 및 오프라인 표시 처리 — 표시 용도로만 쓰고 판단 근거로 삼지 않는다

**하지 않는다**

- AI 모델 직접 호출
- **데이터베이스 직접 조회 및 변경** (`docs/DECISIONS/0002`)
- 어떤 형태로든 Secret 보관
- 관계 단계, 친밀도 등 **핵심 상태를 앱에서 계산하거나 변경**
  (앱은 서버가 계산한 결과를 표시만 한다. 앱의 값은 신뢰하지 않는다)
- 결제 검증 (영수증 검증은 서버에서만 한다)

### 3.2 Samantha Backend

**한다**

- 요청자 인증 및 권한 확인 (Supabase JWT 검증)
- AI Provider 호출 및 응답 스트리밍 중계
- 대화 저장, 장기 기억 추출 및 조회
- 관계 단계 / 친밀도 계산 — **이 계산의 유일한 주체다**
- 안전 정책 적용 (`docs/SAFETY.md`)
- 사용량 제한 및 요금제 확인
- 결제 영수증 검증
- 푸시 알림 발송 판단 및 실행
- 백그라운드 작업 및 정기 실행 작업
- 로깅 / 오류 기록

**하지 않는다**

- 사용자에게 보여줄 문구를 하드코딩 (다국어 확장을 막는다)
- 특정 호스팅 서비스에만 존재하는 기능에 의존 (전환 비용을 키운다)

### 3.3 Supabase

**한다**

- 사용자 인증 (Auth)
- 데이터 저장 (PostgreSQL)
- 행 단위 접근 제어 (RLS)

**하지 않는다**

- AI 호출
- 비즈니스 로직 판단

> **`service_role` 키는 백엔드에만 존재한다.** 앱에는 절대 두지 않는다.

### 3.4 Admin Console (Web)

> 상태: **미구현.** 구조상의 자리와 원칙만 정의한다. 구현 시점은 13장을 본다.

**한다**

- 운영 설정 조회 및 변경 (Companion 성격 문구, 안전 정책 문구, 사용량 한도 등)
- 서비스 상태 및 지표 확인
- 신고 처리 및 계정 제재
- 공지 발송
- 결제 / 구독 상태 조회 및 예외 처리

**하지 않는다**

- Supabase 나 AI Provider 에 직접 연결 (**반드시 Backend 경유**)
- 사용자 대화 내용의 일상적 열람 (아래 원칙)
- 사용자 앱과 인증 체계를 공유

**개인정보 원칙**

- **운영자는 사용자 대화 내용을 함부로 열람하지 않는다.**
- 열람은 신고 처리 등 명확한 사유가 있을 때로 한정하고, **열람 사실을 기록한다.**
- 대화 원문 대신 처리에 필요한 최소 정보만 노출하는 것을 기본으로 한다.

## 4. 백엔드 내부 구조 방향

초기에는 **단일 애플리케이션**으로 만든다. 다만 내부를 역할 단위로 분리해,
나중에 특정 역할을 별도 서비스로 떼어낼 수 있게 한다.

역할 구분(예시이며 구현 시 확정한다):

| 역할 | 담당 |
|---|---|
| 인증 / 사용자 | 토큰 검증, 계정 상태 확인 |
| 대화 | AI 호출, 응답 스트리밍, 대화 저장 |
| 기억 | 기억 추출, 저장, 조회 |
| 관계 | 단계 판정, 친밀도 갱신 |
| 안전 | 입력·출력 정책 검사 |
| 과금 | 사용량 측정, 영수증 검증, 구독 상태 |
| 알림 | 발송 시점 판단, 발송 |

**규칙**: 역할 간 호출은 명시적으로 한다. 데이터베이스를 통해 우회적으로 얽히지 않게 한다.

## 5. 운영 데이터와 코드의 분리

### 5.1 문제

모바일 앱은 스토어 심사를 거친다.
코드에 넣은 값은 한 글자를 바꾸려 해도 앱을 다시 빌드하고 심사를 받아야 하며,
사용자가 업데이트해야 반영된다. **문구 하나 고치는 데 며칠이 걸린다.**

상용 서비스에서는 이것이 곧 장애 대응 속도가 된다.

### 5.2 원칙

**자주 바뀌는 값은 코드가 아니라 데이터로 관리한다.**

| 성격 | 위치 | 예 |
|---|---|---|
| 자주 바뀜 / 운영 중 조정 | **DB (운영 설정)** | Companion 성격 문구, AI 프롬프트, 안전 정책 문구, 사용량 한도, 관계 단계 임계값, 공지 |
| 드물게 바뀜 / 검증 필요 | 코드 | 화면 구성, 데이터 처리 로직, 결제 흐름 |
| 절대 노출 불가 | 백엔드 환경변수 | 각종 Secret |

### 5.3 규칙

- **AI 프롬프트를 앱 코드나 백엔드 코드에 하드코딩하지 않는다.**
- 운영 설정 변경은 **이력을 남긴다.** 누가 언제 무엇을 바꿨는지 추적할 수 있어야 한다.
- 운영 설정이 잘못 입력되어도 서비스가 멈추지 않도록 기본값을 둔다.
- 어떤 값을 운영 설정으로 뺄지는 `docs/DATABASE.md` 에서 확정한다.

## 6. 데이터 흐름 — 대화 1회

```
1. 사용자가 메시지를 입력한다
2. 앱 → 백엔드   (인증 토큰 + 활성 Companion 식별자 + 메시지)
3. 백엔드: 토큰 검증, 활성 Companion 확인, 사용량 한도 확인
4. 백엔드: 안전 정책 검사 (입력)
5. 백엔드: 해당 User × Companion 의 관계 상태와 관련 기억을 조회
6. 백엔드: AI Provider 호출 (프롬프트 = 성격 + 관계 단계 + 기억 + 최근 대화)
7. 백엔드: 안전 정책 검사 (출력)
8. 백엔드 → 앱   (응답 스트리밍)
9. 백엔드: 대화 저장, 사용량 기록
10. [백그라운드] 기억 추출·저장, 관계 상태 갱신
```

- 5번의 조회 범위는 **반드시 해당 User × Companion 으로 한정된다.**
- 10번을 백그라운드로 분리하는 것이 독립 백엔드를 선택한 주된 이유다. (`docs/DECISIONS/0001`)

## 7. 데이터 격리 원칙

`docs/PRODUCT.md` 4장의 제품 정책을 시스템 차원에서 강제한다.

- 대화, 기억, 관계 데이터는 `User` 가 아니라 **`User × Companion`** 단위에 귀속된다.
- **두 Companion 사이에 데이터가 공유되는 경로를 만들지 않는다.**
- 계정 레벨 정보(이메일, 닉네임, 생년월일, 언어, 시간대, 구독 상태)만 공유된다.
- 활성 Companion은 계정당 1명이다. 비활성 Companion에 대해서는
  대화 처리, 알림 발송, 관계 갱신을 수행하지 않는다.
- 비활성 Companion의 데이터는 어떤 경우에도 삭제되거나 변형되지 않는다.

**검증 방법**: 모든 데이터 접근 경로는 Companion 식별자를 필수로 요구한다.
Companion 식별자 없이 대화·기억·관계 데이터를 조회할 수 있는 경로를 만들지 않는다.

`apps/admin/` 은 **자리만 확보하며 지금 구현하지 않는다.**

## 9. 환경 분리

| 환경 | 용도 | Supabase | 백엔드 | 앱 |
|---|---|---|---|---|
| **Development** | 일상 개발. 언제든 초기화 가능 | 개발용 프로젝트 | 로컬 또는 개발 인스턴스 | 개발 빌드 |
| **Staging** | 출시 전 최종 검증. 운영과 동일 구성 | Staging 프로젝트 | Staging 인스턴스 | 내부 배포 빌드 |
| **Production** | 실제 사용자 | 운영 프로젝트 | 운영 인스턴스 | 스토어 배포 빌드 |

### 규칙

- 세 환경은 **데이터베이스, 키, AI 계정을 공유하지 않는다.**
- **Production 데이터를 개발이나 Staging 으로 복사하지 않는다.** (개인정보 보호)
- 앱은 빌드 프로파일로 환경을 구분한다. 앱 실행 중에 환경을 바꿀 수 없게 한다.
- DB 변경은 항상 `Development → Staging → Production` 순서로 적용한다.

### 도입 시점

- Phase 2~4: **Development / Production** 2개로 시작한다.
- 첫 외부 베타 직전에 **Staging** 을 추가한다.
  구조는 처음부터 3환경을 전제로 설계하되, 비용 때문에 도입만 늦춘다.

## 10. 보안 경계

| 자산 | 위치 | 앱에 존재 가능 |
|---|---|---|
| Supabase URL | 앱 / 백엔드 | 가능 (공개 전제) |
| Supabase anon key | 앱 / 백엔드 | 가능 (RLS 로 보호) |
| Supabase `service_role` key | **백엔드만** | 불가 |
| AI Provider API Key | **백엔드만** | 불가 |
| 푸시 발송 자격 증명 | **백엔드만** | 불가 |
| 인앱결제 검증 자격 증명 | **백엔드만** | 불가 |
| 사용자 인증 토큰(JWT) | 앱 (기기 보안 저장소) | 가능 |
| 운영자 인증 자격 증명 | **Admin Console / 백엔드** | 불가 (사용자 앱과 분리) |

### 규칙

- anon key 가 공개되어도 안전하도록, **모든 테이블에 RLS 를 적용한다.**
  앱은 데이터베이스에 직접 접근하지 않지만(`DECISIONS/0002`), 앱에 anon key 가 존재하는 이상
  기술적으로는 접근이 가능하다. 따라서 **RLS 를 2차 방어선으로 유지한다.**
- 백엔드는 모든 요청에서 JWT 를 검증하고, **요청 본문의 사용자 식별자를 신뢰하지 않는다.**
- 관계 단계 등 핵심 상태는 앱이 보낸 값을 신뢰하지 않고 서버가 계산한다.
- **Admin Console 은 사용자 앱과 별도의 인증 체계를 사용한다.** 계정을 공유하지 않는다.
- 운영자 권한은 등급으로 나눈다. 모든 운영자가 모든 것을 할 수 있게 하지 않는다.
- **운영자의 조회 및 변경 행위는 감사 로그로 남긴다.**
- Admin Console 은 Supabase 에 직접 접근하지 않는다. 반드시 백엔드를 경유한다.
- 상세 내용은 `docs/SECURITY.md` 에서 다룬다.

## 11. 국제화 및 확장 대비

한국 출시가 1차 목표이나, **해외 확장을 막는 구조를 만들지 않는다.**

### 언어

- 사용자에게 보이는 문구를 코드에 직접 쓰지 않는다. 키로 관리한다.
- 사용자 언어 설정을 계정 데이터로 저장한다.
- AI 프롬프트도 언어별로 교체 가능한 형태로 설계한다.
- 1.0 에서 제공하는 언어는 한국어뿐이다. **구조만 준비한다.**

### 시간대

- 모든 시각은 **UTC 로 저장한다.** (`timestamptz`)
- 표시할 때 사용자 시간대로 변환한다.
- 사용자 시간대를 계정 데이터로 저장한다.
- **KST 를 코드에 고정하지 않는다.** "먼저 연락" 발송 시각 판단은 사용자 시간대를 기준으로 한다.

### 국가

- 국가별로 달라지는 값(통화, 법적 고지, 연령 정책, 스토어 정책)을
  코드에 상수로 박지 않고 설정으로 분리한다.
- 사용자 국가를 계정 데이터로 저장한다.

## 12. 확장 전략

**현재**: 단일 백엔드 애플리케이션 + 단일 데이터베이스.

**성장 시 분리 후보** (지금 만들지 않는다)

- 백그라운드 작업 처리를 별도 워커로 분리
- 기억 처리를 별도 서비스로 분리
- 읽기 부하 분산

**지금 지켜야 확장이 가능한 것**

- 역할 간 경계를 명확히 유지한다 (4장)
- 특정 호스팅 고유 기능에 의존하지 않는다
- 데이터 접근을 한 곳으로 모아, 나중에 저장소를 바꿔도 영향 범위를 좁힌다
